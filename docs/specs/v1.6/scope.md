# v1.6 スコープ

v1.6 でやること・やらないことを定義します。

## 方針

プレイリストの画像は **アーティスト画像と同じ仕組み** に乗せます。画像ファイルは内容の SHA-256 を名前にして `userData/images/` に置き、DB は `pictures` の行を参照するだけです ([データベース](architecture/database.md))。保存、`media-file://` での配信、孤児の GC はすべて既存の経路を使い、画像のためのストレージを増やしません。

プレイリストは `playlists` / `smart_playlists` に自分の行を持つため、アーティスト (`musics` からの導出で、`artist_pictures` という関連付けテーブルが要る) と違い、**テーブルに `picture_id` 列を足す** だけで済みます。

編集 UI は **アーティスト情報の確認ダイアログを踏襲** します。メニューから開く、Header と Footer は固定でコンテンツだけが一定の高さ、画像タブは `AspectFitPicture` とファイル選択、Apply は変更があるときだけ有効、失敗したら閉じない、という流れをそのまま使います ([プレイリスト情報の確認ダイアログ](features/playlist-info-dialog.md))。通常のプレイリストは編集対象が名前と画像だけなのでタブを分けず、スマートプレイリストはルールが加わるので「詳細」と「画像」のタブに分けます。

サイドバーは **Playlists の項目を Artists の項目に揃え** ます。画像の形 (円と角丸矩形) とスマートプレイリストのバッジ以外は同じ構成にし、行のクラスを共有します ([サイドバーの項目](features/sidebar-rows.md))。Artists の右クリック メニューは Playlists と同じ「hover か選択中に出る右端のメニュー ボタン」に置き換え、両方の項目で「メニューは右端のボタンから」に統一します。

## v1.6 でやること

### データベースと IPC

- マイグレーション 006 で `playlists` と `smart_playlists` に `picture_id INTEGER REFERENCES pictures(id)` を足す ([データベース](architecture/database.md))
- `pictures` の孤児判定にプレイリストの参照を加え、プレイリストの削除と画像の差し替えでも孤児の GC を走らせる
- `mp:playlist:list` / `mp:playlist:update` の返す `Playlist` に `picturePath` と `musicCount` を足す
- `mp:playlist:setPicture` を足す ([IPC](architecture/ipc.md))。Renderer 側は `setPlaylistPicture` コマンドでキャッシュをその場で差し替える

### プレイリスト情報の確認ダイアログ

- サイドバーの項目のメニューとコンテンツ ヘッダーのメニューに「プレイリスト情報の確認」を足す。スマートプレイリストの「ルールを編集」はこれに置き換える ([プレイリスト情報の確認ダイアログ](features/playlist-info-dialog.md))
- 通常のプレイリスト: 名前の入力と画像 (タブなし)
- スマートプレイリスト: 「詳細」タブ (名前とルール。設定ページのような見出しと区切り線で分ける) と「画像」タブ (アーティストのダイアログと同じ)
- ルールのフォームは `SmartRulesDialog` から切り出して、作成ダイアログとこのダイアログで共有する
- Apply で画像 → 名前とルールの順に反映する。いずれかが失敗したらエラーを出して閉じない

### サイドバーの項目

- Playlists の項目を「画像 (角丸矩形)、名前と曲数の 2 段、右端のメニュー ボタン」にする ([サイドバーの項目](features/sidebar-rows.md))
- 画像がなければ現在のアイコン (`ListMusic` / `Sparkles`) をプレースホルダーとして出す
- 画像のあるスマートプレイリストは、画像の右下に `Asterisk` アイコンのバッジを重ねて見分ける
- Artists の項目のメニューを右クリックから右端のメニュー ボタン (hover か選択中に表示) に変え、Playlists と同じ位置、同じ見た目にする
- 選択中の項目ではメニューのアイコンも文言と同じ反転色にする

### コンテンツ ヘッダー

- Playlists のヘッダー左端のタイルを、画像があれば画像にする。スマートプレイリストはサイドバーと同じバッジを重ねる ([プレイリスト ヘッダー](features/playlist-header.md))

### 公式サイト

- トップ ページの「Playlists and smart playlists」の説明に画像を足し、サイドバーが写るスクリーンショットを撮り直す ([公式サイトへの反映](features/web-site.md))

## v1.6 でやらないこと

| 機能 | 備考 |
| --- | --- |
| 画像の削除 (未設定に戻す) | アーティスト画像にもない。差し替えだけにする。v1.x でアーティストと一緒に検討する |
| 画像の自動設定 (先頭の曲のアートワークなど) | プレイリストは曲の集まりで代表アートワークを決めにくい。画像のないプレイリストはプレースホルダーのアイコンのまま |
| ドラッグ & ドロップやクリップボードからの画像の設定 | ファイル選択だけ。アーティスト画像と同じ |
| サイドバーのインライン名前変更の廃止 | ダブルクリックとメニューの「名前を変更」は残す。ダイアログを開くまでもない 1 項目の変更に向く |
| サイドバーの項目の並べ替え | `sortOrder` は今までどおり Main が受け付けるだけで、UI は持たない |
| Artists の項目の仮想スクロールを Playlists にも入れる | プレイリストの数は多くて数十件。今までどおり通常の並びにする |
| プレイリスト画像の MusicBrainz からの取得 | 対象外 |
| 曲情報 / アルバム情報ダイアログのメニュー配置の変更 | 曲行とアルバム見出しのメニューは変えない。変えるのはサイドバーの 2 つの項目だけ |

## 非機能要件

- 画像ファイルの検証 (空、未対応の MIME) と保存は `onSetArtistPicture` と同じ関数を使い、プレイリスト用の分岐を増やさない
- 孤児の GC はプレイリストを含む 1 つの関数 (`deleteOrphanedPictures`) で判定し、画像ファイルの削除はトランザクションのコミット後に行う (既存の規則)
- 一覧クエリに足す `musicCount` は、静的は `COUNT` の 1 クエリ、スマートはルールの `COUNT(*)` で求める。1 万曲のライブラリーでスマートプレイリストが 10 件あっても一覧の取得が体感できるほど遅くならない (各数ミリ秒)
- サイドバーの 2 つの項目は行のクラスを共有し、hover の発光、選択中の塗り、反転色が 1 か所で決まる
- ダイアログの判定 (Apply の可否、変更の有無、保存する patch の組み立て) は純関数にし、ユニット テストで押さえる (jsdom は入れず、hook の判定を純関数に切り出す既存の方針)
- 壊れたルールのスマートプレイリスト (`rules` なしで一覧に出るもの) もダイアログを開け、ルールを入れ直して Apply すれば復旧できる
